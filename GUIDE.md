# Norn

[![CI](https://github.com/stra-ta/norn/actions/workflows/ci.yml/badge.svg)](https://github.com/stra-ta/norn/actions/workflows/ci.yml)
[![License](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Norn is a header-only C++20 library for studying bounded queues, memory
ordering, and hazard-pointer reclamation.
It is a pre-1.0 lab library, not a production-maturity claim.

## Evidence

Functional verification and performance measurement are separate.
CTest proves queue contracts and test-tool invariants.
The benchmark programs produce performance evidence only.

Run [`tools/verify.sh`](tools/verify.sh) for the Debug functional suite.
Run [`tools/full_confidence.sh`](tools/full_confidence.sh) for isolated Debug,
ASan, and UBSan suites.

The historical queue comparison is preserved in
[`docs/evidence/benchmarks/legacy-5d73d0eb.json`](docs/evidence/benchmarks/legacy-5d73d0eb.json).
It records commit, dirty state, compiler, kernel, CPU, architecture, build
type, command, and workload metadata.
Its figure is generated by
[`tools/generate_benchmark_figure.py`](tools/generate_benchmark_figure.py), and
CI checks that the committed SVG still matches the JSON input.

![Historical queue throughput](docs/BENCHMARKS.svg)

The historical measurements include thread setup in the timed workload.
They describe one Apple M1 run from commit `5d73d0eb` and are not portable
performance claims.

The hardware campaign summary in
[`docs/evidence/hardware/2026-08-22-pilot/summary.json`](docs/evidence/hardware/2026-08-22-pilot/summary.json)
is an exploratory M1 and virtualized Linux ARM64 pilot.
It records per-sample throughput, run-level latency, retries, yields, spin
steps, fairness, context switches, and affinity read-back.
No x86-64 or bare-metal Linux performance result is published here.

## Architecture

![Norn architecture](docs/ARCHITECTURE.svg)

Norn has three queue families and a small set of shared core utilities.

| Structure | Ownership | Storage | Contract boundary |
| --- | --- | --- | --- |
| `mutex_queue<T>` | Multiple producers and consumers | `std::deque` | Blocking reference queue with close-and-drain semantics |
| `bounded_mutex_queue<T, N>` | Multiple producers and consumers | Fixed ring | Bounded locking baseline |
| `spsc_ring<T, N>` | One producer and one consumer | Pre-allocated ring | Acquire/release publication |
| `spsc_ring_padded<T, N>` | One producer and one consumer | Pre-allocated ring | Cache-line placement experiment |
| `mpmc_ring<T, N>` | Multiple producers and consumers | Sequence-number ring | CAS reservation with documented reservation gaps |
| `mpsc_linked_queue<T>` | Multiple producers and one consumer | Heap nodes | Hazard-protected deferred reclamation |

Core headers under `include/norn/core/` provide cache-line alignment, atomic
placement, CPU pause hints, and retry policies.
The reusable hazard primitives live in `include/norn/hazard/`.
`include/norn/hazard_pointer.hpp` remains an umbrella compatibility header.

The SPSC ring is wait-free only under its single-producer and single-consumer
ownership contract.
The MPMC ring is mutex-free and non-blocking, but Norn makes no formal
lock-free claim for it.
The linked queue makes no lock-free or wait-free claim because allocation and
reclamation scans affect progress.

The linked queue accepts an optional `std::pmr::memory_resource` for controlled
allocation tests.
Its default resource is `std::pmr::new_delete_resource()`.

## Build

Requirements are CMake 3.25 or newer, a Make or Ninja generator, and a C++20
compiler.

The default configuration builds tests and benchmarks when Norn is the
top-level project:

```sh
cmake --preset default
cmake --build --preset default
ctest --preset default --output-on-failure
```

The project applies `-Wall -Wextra -Wpedantic -Wconversion -Wshadow -Werror`
to its own GCC and Clang targets.
Installed consumers do not inherit those project-only warning flags.

Install the header-only package with:

```sh
cmake --preset release
cmake --build --preset release
cmake --install build/release --prefix <prefix>
```

Consume it with:

```cmake
find_package(norn CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE norn::norn)
```

Configure the consumer with `-DCMAKE_PREFIX_PATH=<prefix>` when the prefix is
outside the default search paths.

## Verification

The test suite covers queue boundaries, wraparound, move-only values, FIFO and
exactly-once histories, close-and-drain behavior, progress-window
demonstrations, hazard publication, slot exhaustion, registration lifecycle,
reclamation, and allocator failure.

The source-level memory-order gate checks the acquire/release and sequentially
consistent fence points.
Its self-test mutates a release operation in memory and verifies that the gate
rejects the mutation.

The CMake presets include `default`, `debug`, `release`, `asan`, `ubsan`, and
`tsan`.
The local full suite runs Debug, ASan, and UBSan.
TSan remains an opt-in profile because the local Apple toolchain does not
support this repository's atomic-fence configuration.

The hardware campaign is explicit about functional versus performance
evidence.
It can collect cycles, instructions, branches, branch misses, cache
references, cache misses, context switches, CPU migrations, and task-clock
counters when Linux permissions expose them.
Unavailable counters stay marked unavailable.

Read [`docs/CORRECTNESS.md`](docs/CORRECTNESS.md) for contracts and
[`docs/HAZARD_POINTER_DESIGN.md`](docs/HAZARD_POINTER_DESIGN.md) for the
reclamation protocol.
Read [`docs/BENCHMARKING.md`](docs/BENCHMARKING.md) and
[`docs/HARDWARE_PERFORMANCE.md`](docs/HARDWARE_PERFORMANCE.md) before using
any measurement.

## Limitations

- `mpmc_ring` is not formally lock-free despite using atomics and no mutex.
- `mpsc_linked_queue` is MPSC and makes no lock-free or wait-free claim.
- Hazard-domain registration is explicit at thread exit, and a thread must
  deregister before switching to another domain.
- A hazard domain and the queue's memory resource must outlive all queue
  operations and deferred reclamation.
- Baseline benchmark setup is part of the timed workload.
- Run-level latency is an aggregate elapsed-time-per-item measure, not a
  per-operation latency distribution.
- Native x86-64 verification comes from CI functional runs, not performance
  evidence.
- The Linux ARM64 pilot is virtualized and does not establish physical cache,
  NUMA, or bare-metal scheduler claims.
